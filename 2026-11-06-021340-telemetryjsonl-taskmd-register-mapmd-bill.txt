● Both answers are partly right, with a few misses.

  Q1: Why not last reading minus first reading?

  What you got right: missing readings matter. The M1 gap is an example.

  What doesn't fit:
  - Peak timing is a separate calculation. Peak power is the highest valid power
    reading, and it doesn't touch energy.
  - M3's extra register is a decoding detail. It changes which array position
    holds each value, not how energy is calculated.

  The real reasons, all in this data:
  1. Rollover. M2's counter wraps past 2³² and restarts near 0 on 25 Oct. Last
     minus first would come out hugely negative.
  2. Reset. M3 lost power on 26 Oct and its counter fell back to an older saved
     value. Last minus first would quietly include that corrupted jump, so rule
     6 ("never invent energy") would be violated. Only per-interval handling
     lets you spot that one interval and count it as 0.
  3. Gaps. Without intervals you can't tell which parts of the day were measured
     and which were missed.
  4. Day boundaries. Rule 3 gives each interval to the day it starts. An
     interval beginning at 23:55 belongs to the earlier day even though it ends
     after midnight, so "first and last reading of the day" gives the wrong
     split.
  5. The 25-hour day. The DST hour makes "first and last of the day" ambiguous.

  Q2: Why sort by gw_seq rather than timestamp?

  One correction: timestamps aren't the ones that go missing. I checked, and
  gw_seq runs 50001–52618 with no gaps at all. Missing reads simply show up as
  timestamp gaps between consecutive sequence numbers.

  What you got right: the duplicates point. Sorting or deduplicating by
  timestamp is dangerous, and the DST hour shows why. Two reads can share the
  same ts string (for example 02:05:00 on 25 Oct) and be genuinely different
  measurements. If we dropped them as duplicates we'd throw away real data. A
  true duplicate repeats the same gw_seq, so that's the safe key.

  The full reason:
  1. DST. The repeated hour makes ts ambiguous and makes it jump backwards.
     gw_seq always increases.
  2. Delivery order. Messages arrive out of order (245 lines in this file), so
     file order can't be trusted either.
  3. Safe deduping. Same gw_seq means the same message, so it's a safe key for
     removing QoS 1 redeliveries.
